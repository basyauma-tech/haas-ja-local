# MLX版の精度と速度（Mac、2026-11-08）

MLX版（エンコーダbf16、予測ネットワークと結合ネットワークfloat32）をasr-ja-bench v1.1のFLEURSとJVNVで測った。CER strictはFLEURS 3.65%、JVNV 4.51%で、どちらも公表値の幅の中に入った（合格基準は公表値との差0.3ポイント以内）。速度はバッチ1・1発話ずつで実時間の約250倍だった。

33.8分の音声1本も最後まで通った。ただし次の2点が見つかった。詳しくは後述する。

- 長時間音声ではCERが悪化する。1発話ずつなら4.10%の音声が、30秒ごとに分けて認識すると6.44%になった。torch（fp32）でも6.39%なので、MLXの数値誤差ではない。
- mlxのバッファキャッシュが際限なく増えていた。macOSのメモリフットプリントは約14GBに達した。実際に使っているメモリは1.25GBで一定で、リークではない。これを受けて`HaasMLX.load`がキャッシュの上限を既定で1GiBに抑えるようにした。上限を入れた後は、同じ音声でフットプリントが3.48GBになり、書き起こしは変わらなかった。

数値はすべて`var/bench/results/`以下のファイルから取った（`var/`はGit管理外）。各節に出典のファイルを書く。

## 評価データ

- [third-intelligence/asr-ja-bench](https://huggingface.co/datasets/third-intelligence/asr-ja-bench) v1.1を、データセット付属の`rebuild.py`で`var/bench/asr-ja-bench-v1.1/`に再構築した。`fleurs.jsonl`は650行、`jvnv.jsonl`は1,375行。書き起こしはすべて`rebuild.py`のハッシュ照合を通った。
  - 使った`rebuild.py`のSHA-256は`886ab3967fb60c3c3c68b357721c083b83a11b66e76400c34eab84000fd82900`（`var/bench/asr-ja-bench-src/`に保存）。Hugging Faceのキャッシュに残るmainの参照は`e60cb55dedc9ffba954852dcc86f8c1210b95de0`。
  - JVNVは公式サイトの`jvnv_ver1.zip`（SHA-256 `6d7f5334c2288dcb92730858d8c4a8dd6e62781f02755e56e611d9844ed9bd99`）から作った。
  - `rebuild.py`は「ffmpeg 7.1で音声がビット単位で再現する」と書いている。今回はffmpeg 9.0.2を使ったので、48kHzから16kHzへ変換したJVNVの音声は公式の評価音声とわずかに違う可能性がある。書き起こしはハッシュで一致を確認済み。FLEURSはHugging Faceから16kHzで取るのでffmpegを通らない。
- ライセンス: FLEURSはCC BY 4.0、JVNVはCC BY-SA 4.0。評価音声と書き起こしは手元で使うだけで、リポジトリには含めず再配布もしない。
- 再構築の手順は`scripts/rebuild_bench.py`にまとめた（今回のデータは同じ`rebuild.py`を直接実行して作ったもので、このラッパーでは作り直していない）。

```sh
uv run --extra eval python scripts/rebuild_bench.py --subset fleurs jvnv \
  --jvnv-zip var/bench/jvnv_ver1.zip --out var/bench/asr-ja-bench-v1.1
```

## 精度

1発話ずつ`pipeline.transcribe`に通し、サブセット全体を`jacer.cer(refs, hyps, jacer.METRICS)`で1回計算した。これはコーパス単位のマイクロ平均で、公式の評価と同じ集計である。jacerは3指標とも句読点と空白を採点しない（`jacer.cer(["今日は晴れです"], ["今日は、晴れです。"])`は3指標とも0）。30秒を超える発話はなかったので、長時間音声の分割は一度も使っていない（`n_longform`は0）。最長はFLEURS 28.2秒、JVNV 19.2秒。

```sh
uv run --extra eval --extra mlx python scripts/eval_bench.py --model var/dist/mlx --backend mlx \
  --bench var/bench/asr-ja-bench-v1.1 --subset fleurs jvnv --out var/bench/results/mlx-bf16
```

| サブセット | 発話数 | 音声（時間） | CER strict | CER flex | CER kana | 公表値strict | 差（ポイント） | 判定 |
|---|---:|---:|---:|---:|---:|---:|---:|---|
| FLEURS | 650 | 2.36 | 3.65 | 2.98 | 2.33 | 3.65〜3.67 | 0.00 | 合格 |
| JVNV | 1,375 | 3.33 | 4.51 | 3.06 | 2.25 | 4.50〜4.53 | 0.00 | 合格 |

- 値は%。strictの小数第3位まではFLEURS 3.655、JVNV 4.514。
- 公表値はasr-ja-bench v1.1での公式の測定（NeMo、bf16、H200）。モデルカードと公開記事で小数第2位が違うため、両方を幅で示した。差は幅の近い端からの差で、幅の中なら0とした。flexとkanaは公表値との照合をしていない。
- 精度を合わせるための調整は何もしていない。1回目の実行の数値をそのまま載せた。
- 出典: `var/bench/results/mlx-bf16/{fleurs,jvnv}/summary.json`、発話ごとの書き起こしは同じディレクトリの`hyps.jsonl`、表は`summary.md`。

## 速度とメモリ

条件: バッチ1、1発話ずつ、Metal、エンコーダbf16／予測ネットワークと結合ネットワークfloat32。モデル読み込み後、先頭3発話をウォームアップとして除いた（初回のカーネル準備はここに入る）。処理時間は音声ファイルの読み込みを除いた`transcribe`だけの時間。FLEURS全650発話のうち647発話で集計した。

```sh
uv run --extra mlx python scripts/bench_speed.py --model var/dist/mlx --backend mlx \
  --bench var/bench/asr-ja-bench-v1.1 --subset fleurs --out var/bench/results/mlx-bf16-speed.json
```

| 項目 | 値 |
|---|---:|
| RTFx（1発話ごとの中央値） | 250.9 |
| RTFx（1発話ごとの平均） | 253.7 |
| RTFx（合計音声2.35時間÷合計処理33.1秒） | 255.9 |
| 1発話の処理時間（中央値） | 0.050秒 |
| モデル読み込み | 0.15秒（ファイルがOSのキャッシュに載った状態） |
| ピークRSS（`getrusage`の`ru_maxrss`） | 2.68GB（読み込み直後は1.30GB） |
| mlxのピーク割り当て（`mx.get_peak_memory()`） | 1.82GB（読み込み直後は1.26GB） |
| macOSのピークメモリフットプリント（`/usr/bin/time -l`） | 14.40GB（キャッシュ上限を入れる前。再実行時に測定） |

- GBは10^9バイト。
- 出典: `var/bench/results/mlx-bf16-speed.json`（1発話ごとの時間も入っている）。同じコマンドを`/usr/bin/time -l`の下で再実行した結果は`var/bench/results/aux/mlx-bf16-speed-rerun.json`と`aux/speed-time.txt`にある。再実行では中央値248.5、合計252.2で、差は2%以内だった。
- 精度の評価中に測ったRTFx（ウォームアップ1発話を除く）はFLEURS 251.5、JVNV 228.3（`mlx-bf16/*/summary.json`の`rtfx`）。
- 公表のRTFx（H200、バッチ512）とは条件がまったく違うので比べられない。
- メモリフットプリントがRSSよりずっと大きいのは、mlxが解放したMetalバッファをキャッシュとして持ち続けるためである。長時間音声の節で詳しく測った。
- 上の表は、キャッシュ上限（1GiB）を既定にする前の測定である。既定にした後に同じコマンドを`/usr/bin/time -l`の下で再実行すると、RTFx中央値254.2、合計256.1、ピークRSS 1.57GB、mlxのピーク割り当て1.76GB、ピークメモリフットプリント3.19GBだった（`aux/mlx-bf16-speed-capped.json`、`aux/speed-time-capped.txt`）。速度は変わらず、フットプリントだけが下がった。

## 長時間音声

FLEURSの先頭150発話（`fleurs.jsonl`の順）を0.5秒の無音を挟んでつなぎ、33.8分（2,026.5秒）の音声を作った。ファイル名は計画にあわせて`fleurs_concat_20min.flac`としたが、実際の長さは33.8分である。使った発話のidと開始秒は`var/bench/long/fleurs_concat_20min.json`にある。

```sh
uv run python scripts/long_audio.py make --bench var/bench/asr-ja-bench-v1.1 --subset fleurs --count 150 \
  --out var/bench/long/fleurs_concat_20min.flac
/usr/bin/time -l .venv/bin/haas-ja-local transcribe var/dist/mlx var/bench/long/fleurs_concat_20min.flac \
  --json --timestamps > var/bench/long/out.json
uv run --extra eval python scripts/long_audio.py score --audio var/bench/long/fleurs_concat_20min.flac \
  --transcript var/bench/long/out.json --hyps var/bench/results/mlx-bf16/fleurs/hyps.jsonl \
  --out var/bench/results/mlx-bf16-long.json
```

`uv run`越しに`/usr/bin/time`を掛けた場合も、出力と最大RSSはほぼ同じだった（7.58秒、2.06GB）。上の表は`.venv/bin`を直接実行した値。

| 項目 | MLX | torch（参考、CPU fp32） |
|---|---:|---:|
| 所要時間（プロセス起動とモデル読み込みを含む） | 7.34秒（RTFx 276） | 109.26秒（RTFx 18.5） |
| 最大RSS | 2.06GB | 6.39GB |
| macOSのピークメモリフットプリント | 13.96GB（キャッシュ上限を入れる前） | - |
| 分割数 | 68 | 68 |
| トークン数 | 6,252 | 6,262 |
| トークン開始時刻が単調非減少か | はい | はい |
| 最後のトークンの終了時刻（音声長2,026.48秒） | 2,025.15秒 | 2,025.15秒 |
| CER strict / flex / kana（%） | 6.44 / 5.75 / 4.75 | 6.39 / 5.70 / 4.62 |

出典: `var/bench/results/mlx-bf16-long.json`、`var/bench/results/torch-fp32-long.json`、`var/bench/results/aux/long-mlx-time.txt`、`aux/long-torch-time.txt`。正解文は150発話の正解文を区切りなしで連結したもの。

分割認識は最後まで通り、時刻も音声の終わりまで並んだ。CERの悪化について次を確かめた。

| 認識のしかた | CER strict（%） | 出典 |
|---|---:|---|
| 1発話ずつ認識して連結（`hyps.jsonl`） | 4.10 | `mlx-bf16-long.json`の`cer_per_utterance_concat` |
| 発話を切らずに30秒以内のまとまり（86個）にして1回ずつ認識 | 5.08 | `aux/long-grouped-mlx.txt` |
| 33.8分を30秒前後で分割して認識（CLIと同じ） | 6.44 | `mlx-bf16-long.json`の`cer_longform` |
| 同上、torch（fp32） | 6.39 | `torch-fp32-long.json` |

- MLXとtorchがほぼ同じなので、悪化の原因はMLXの数値誤差ではない。モデルと分割のしかたによるものである。
- 発話を切らずにまとめただけで約1ポイント悪化した。話者の違う発話を0.5秒の間隔で並べた音声は、モデルにとって不自然な入力である。この悪化は、実際の録音（同じ話者が続けて話す）では小さい可能性がある。
- 残る約1.4ポイントは、発話の途中で切ったことによる。分割位置は目標±2秒の範囲で最も静かな0.1秒窓の中心なので、67か所の境界のうち50か所が発話の途中だった（`aux/long-attribution.txt`）。
- 差分を見ると、句読点の脱落（採点対象外）のほかに、境界から離れた位置での語の置換や、文1つ分の脱落があった（例: 境界から約14秒離れた位置で「海の下は薄く、工地の下は厚くなっています」が丸ごと抜けた）。境界の近くだけで起きている現象ではない。
- 発話ごとの内訳は、トークンの時刻で発話に割り当てて計算すると割り当ての誤差が混ざるため、参考値にとどめる（`aux/long-attribution.txt`）。

### mlxのバッファキャッシュ

mlxは解放した配列のMetalバッファを再利用のために持ち続ける。断片ごとに長さが違うと再利用されにくく、キャッシュが増え続ける。同じ33.8分の音声で、断片ごとに測った値は次のとおり（`aux/memtrace.py`でモデル読み込み後の認識だけを測った。出典は`aux/long-mlx-cache-limit.txt`）。

| 断片 | 使用中のメモリ | キャッシュ | フットプリント |
|---:|---:|---:|---:|
| 0 | 1.25GB | 0.67GB | 2.42GB |
| 32 | 1.25GB | 9.49GB | 11.34GB |
| 67（最後） | 1.25GB | 12.09GB | 13.97GB |

使用中のメモリは一定で、リークはない。ただし利用者から見たメモリ使用量（アクティビティモニタの「メモリ」）は約14GBになる。この機種でのmlxの既定のキャッシュ上限は130.6GB（`mx.set_cache_limit`が返す既定値。`aux/mlx-cache-limit-default.txt`）で、実質的に上限がない。上限は搭載メモリに応じて決まるので、メモリの少ない機種では低い値で頭打ちになるはずだが、手元では確かめていない。

キャッシュ上限を1GBにした場合（`mx.set_cache_limit(10**9)`）の比較は次のとおり。

| キャッシュ上限 | 認識の所要時間 | 最後のフットプリント |
|---|---:|---:|
| なし（既定） | 7.04秒 | 13.97GB |
| 1GB | 7.27秒 | 2.90GB |

この結果を受けて、`HaasMLX.load`がキャッシュの上限を既定で1GiB（2^30バイト）に設定するようにした。引数`cache_limit_bytes`で変えられ、`None`なら設定しない。上限はプロセス全体の設定なので、現在の上限のほうが小さい場合は変えない（利用者が設定した値を上げない）。

既定にした後、同じ33.8分の音声をCLIで再実行した（`/usr/bin/time -l .venv/bin/haas-ja-local transcribe ...`）。

| 項目 | 上限なし（変更前） | 1GiB（変更後の既定） |
|---|---:|---:|
| 所要時間（プロセス起動とモデル読み込みを含む） | 7.34秒 | 6.97秒 |
| 最大RSS | 2.06GB | 1.74GB |
| macOSのピークメモリフットプリント | 13.96GB | 3.48GB |
| 書き起こし（`--json --timestamps`の出力） | - | 変更前とバイト単位で同一 |

出典: `aux/long-mlx-time.txt`、`aux/long-mlx-time-capped.txt`。変更前の出力は`aux/long-mlx-out-before-cap.json`に退避した。

## 追加の確認: 予測ネットワークと結合ネットワークをCPUで動かす場合

`HaasMLX.step`全体を`with mx.stream(mx.cpu):`で動かすと、`MLX_ENABLE_TF32`の既定を設定しなくてよくなる可能性がある。そこで速度を比べた。FLEURSの先頭103発話のうち、ウォームアップ3発話を除く100発話で測った。各条件を2回ずつ実行した（`aux/step-stream-check.txt`、`aux/stream_check.py`）。

| 条件 | RTFx中央値（1回目／2回目） | 既定とトークン列が一致した発話 |
|---|---:|---:|
| 既定（GPU、TF32オフ） | 251.9 / 245.4 | - |
| `step`をCPUストリームで実行 | 205.3 / 206.4 | 100/100 |
| GPU、`MLX_ENABLE_TF32=1` | 244.0 / 252.5 | 100/100 |

CPUストリームにすると約2割遅くなるので、既定は変えない。TF32のオン・オフで速度もトークン列も変わらなかった（100発話の範囲）。

## 未測定

- asr-ja-benchの残りのサブセット（JSUT、TEDxJP-10K、SpeechBSD）。
- x86_64機、Linux、Windows。
- バッチ2以上。
- 実際の長時間録音（同じ話者が続けて話す音声）。今回の長時間音声は発話をつないだもの。
- メモリの少ない機種（16GB以下）での動作とメモリ使用量。
- ONNX版（fp32・int8）。別の記録で扱う。
