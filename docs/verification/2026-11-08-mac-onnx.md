# ONNX版の精度と速度（Mac、2026-11-08）

`.nemo`から書き出したONNX版（fp32とint8）を、Apple SiliconのCPU（ONNX Runtime）で検証した。

- fp32はtorch（float32）と数値が一致した。CER strictはFLEURS 3.69%、JVNV 4.52%で、どちらも合格した（合格基準は公表値との差0.3ポイント以内）。FLEURS全650発話の書き起こしもtorchと完全に一致した。
- int8（ONNX Runtimeの動的量子化）はFLEURSで不合格だった（CER strict 4.05%、差0.38ポイント）。デコーダをfp32のままにしても4.09%で、改善しなかった。int8は参考として配り、既定はfp32のままにする。
- 速度はバッチ1・1発話ずつで実時間の約65〜85倍だった。

数値はすべて`var/bench/results/`と`var/verify/`以下のファイルから取った（`var/`はGit管理外）。各節に出典のファイルを書く。

## 書き出し

```sh
/usr/bin/time -l uv run --extra convert haas-ja-local convert-onnx \
  --nemo var/upstream/Haas-ja-v1.0.nemo --out var/dist/onnx --int8
```

| 項目 | 値 |
|---|---:|
| 所要時間（`uv run`の起動とパッケージの再ビルドを含む） | 19.98秒 |
| 最大RSS | 8.39GB |
| fp32: `encoder.onnx` + `encoder.onnx.data` | 0.74MB + 2,435.4MB |
| fp32: `decoder_joint.onnx` | 27.7MB |
| int8: `encoder.onnx` + `encoder.onnx.data` | 3.2MB + 609.8MB |
| int8: `decoder_joint.onnx` | 7.1MB |

- GBは10^9バイト、MBは10^6バイト。
- 同じコマンドに`--exclude-decoder`を付けて`var/dist/onnx-excl`へ書き出し直すと、fp32の3ファイルとint8のエンコーダはバイト単位で同じだった（`SHA256SUMS`が一致）。書き出しの再現性を確認できた。
- 量子化では、各層の`self_attn/Slice`などで「型を推論できないので量子化しない」という警告が出た。重みの量子化は完了している。
- 出典: `var/bench/results/aux/onnx-export-time.txt`、`aux/onnx-export-stdout.txt`、`aux/onnx-excl-export-time.txt`。

## 数値の一致（fp32）

FLEURSの6発話で、書き出したONNX版（fp32）と自前のtorch実装（float32）を比べた。melと貪欲探索には、外部のONNX書き出しに付属する参照実装を使った。

```sh
uv run --with librosa --extra convert --extra onnx python scripts/verify_numerics.py \
  --nemo var/upstream/Haas-ja-v1.0.nemo --reference-dir var/reference/sanami-onnx \
  --clips var/bench/clips --onnx-dir var/dist/onnx/fp32 --out var/verify/onnx-fp32.json
```

| 項目 | 6発話の最大 | 合格基準 | 判定 |
|---|---:|---:|---|
| (a) melの最大絶対差 | 9.54e-07 | 1e-3未満 | 合格 |
| (b) エンコーダ出力の相対誤差 | 3.82e-06 | 1e-4未満 | 合格 |
| (c) 結合ネットワークのlogitsの相対誤差 | 1.11e-06 | 1e-4未満 | 合格 |
| (c) 予測ネットワークの状態の相対誤差 | 1.15e-06 | - | - |
| melとエンコーダ出力のフレーム数の一致 | 6/6 | 6/6 | 合格 |
| (d) トークン列の一致（torchの貪欲探索とONNXの貪欲探索） | 6/6 | 6/6 | 合格 |

- (b)と(c)は1e-5も下回った。
- 出典: `var/verify/onnx-fp32.json`、`var/verify/onnx-fp32.log`（発話ごとの表と書き起こし）。

## 精度

1発話ずつ`pipeline.transcribe`に通し、サブセット全体を`jacer.cer(refs, hyps, jacer.METRICS)`で1回計算した（コーパス単位のマイクロ平均）。ONNX Runtimeのスレッド数は8。30秒を超える発話はなく、長時間音声の分割は使っていない（`n_longform`は0）。

```sh
uv run --extra eval --extra onnx python scripts/eval_bench.py --model var/dist/onnx --backend onnx \
  --variant fp32 --threads 8 --bench var/bench/asr-ja-bench-v1.1 --subset fleurs jvnv \
  --out var/bench/results/onnx-fp32
```

int8は`--variant int8 --out var/bench/results/onnx-int8`、デコーダをfp32のままにしたint8は`--model var/dist/onnx-excl --variant int8 --out var/bench/results/onnx-int8-excl`で実行した。

| 版 | サブセット | CER strict | CER flex | CER kana | 公表値strict | 差（ポイント） | 判定 |
|---|---|---:|---:|---:|---:|---:|---|
| fp32 | FLEURS | 3.69 | 3.02 | 2.38 | 3.65〜3.67 | +0.02 | 合格 |
| fp32 | JVNV | 4.52 | 3.06 | 2.25 | 4.50〜4.53 | 0.00 | 合格 |
| int8 | FLEURS | 4.05 | 3.35 | 2.50 | 3.65〜3.67 | +0.38 | 不合格 |
| int8 | JVNV | 4.43 | 3.16 | 2.33 | 4.50〜4.53 | -0.07 | 合格 |
| int8（デコーダはfp32） | FLEURS | 4.09 | 3.38 | 2.50 | 3.65〜3.67 | +0.42 | 不合格 |
| int8（デコーダはfp32） | JVNV | 4.40 | 3.14 | 2.33 | 4.50〜4.53 | -0.10 | 合格 |

- 値は%。発話数はFLEURS 650（2.36時間）、JVNV 1,375（3.33時間）。
- 公表値はasr-ja-bench v1.1での公式の測定（NeMo、bf16、H200）。モデルカードと公開記事で小数第2位が違うため、両方を幅で示した。差は幅の近い端からの差で、幅の中なら0とした。
- fp32のFLEURS 3.69%は、MLX版の記録にあるtorch（float32）の3.69%と同じだった。FLEURS全650発話で、fp32の書き起こしはtorchと650/650一致した。int8は305/650、デコーダをfp32のままにしたint8も305/650だった（`aux/onnx-vs-torch-text.json`）。
- int8の精度が悪化した原因はエンコーダの量子化である。デコーダをfp32のままにしても改善しなかった。
- int8は既定のint8（デコーダも量子化）を参考として配る。FLEURSでの差が小さく、ファイルも小さいためである。既定の版はfp32のまま変えない。
- 精度を合わせるための調整は何もしていない。量子化の設定（per-channel、`reduce_range=False`、前処理なし）も変えていない。
- 3つの評価は実行時間が重なったので、評価中のRTFxは使わない。速度は次の節で別に測った。
- 出典: `var/bench/results/{onnx-fp32,onnx-int8,onnx-int8-excl}/{fleurs,jvnv}/summary.json`、発話ごとの書き起こしは同じディレクトリの`hyps.jsonl`。

## 速度とメモリ

条件: バッチ1、1発話ずつ、CPUのみ。モデル読み込み後、先頭3発話をウォームアップとして除き、FLEURSの647発話で集計した。処理時間は音声ファイルの読み込みを除いた`transcribe`だけの時間。ほかの重い処理は実行していない。

```sh
uv run --extra onnx python scripts/bench_speed.py --model var/dist/onnx --backend onnx --variant fp32 \
  --threads 4 --bench var/bench/asr-ja-bench-v1.1 --subset fleurs \
  --out var/bench/results/onnx-fp32-t4-speed.json
```

| 版 | スレッド | RTFx中央値 | RTFx平均 | RTFx合計 | 1発話の中央値 | 読み込み | ピークRSS（読み込み直後） |
|---|---:|---:|---:|---:|---:|---:|---:|
| fp32 | 4 | 72.4 | 72.4 | 72.7 | 0.173秒 | 1.11秒 | 3.24GB（2.27GB） |
| fp32 | 12 | 66.7 | 66.1 | 66.4 | 0.184秒 | 1.03秒 | 3.24GB（2.27GB） |
| int8 | 4 | 70.0 | 69.7 | 69.8 | 0.178秒 | 1.35秒 | 1.41GB（0.66GB） |
| int8 | 12 | 84.3 | 83.8 | 84.3 | 0.150秒 | 0.91秒 | 1.40GB（0.66GB） |

- RTFx合計は合計音声2.35時間÷合計処理時間。ピークRSSは`getrusage`の`ru_maxrss`。読み込みはファイルがOSのキャッシュに載った状態の値。
- 12スレッドはPerformanceコアの数に合わせた。この機種ではSuperコア（6）とPerformanceコア（12）が混在し、12スレッドは両方にまたがる。
- fp32は12スレッドのほうが遅かった。再実行でも中央値は4スレッド71.8、12スレッド65.0で、結果は同じ傾向だった（`aux/onnx-fp32-t{4,12}-speed-rerun.json`）。原因は調べていない。
- 公表のRTFx（H200、バッチ512）とは条件がまったく違うので比べられない。
- 出典: `var/bench/results/onnx-{fp32,int8}-t{4,12}-speed.json`（1発話ごとの時間も入っている）。

## 長時間音声

MLX版の記録と同じ33.8分（2,026.5秒）の音声を使った。FLEURSの先頭150発話を0.5秒の無音を挟んでつないだもので、CLIでfp32を指定し、スレッド数は既定のまま認識した。

```sh
/usr/bin/time -l .venv/bin/haas-ja-local transcribe var/dist/onnx var/bench/long/fleurs_concat_20min.flac \
  --backend onnx --variant fp32 --json --timestamps > var/bench/long/out-onnx-fp32.json
uv run --extra eval python scripts/long_audio.py score --audio var/bench/long/fleurs_concat_20min.flac \
  --transcript var/bench/long/out-onnx-fp32.json --hyps var/bench/results/onnx-fp32/fleurs/hyps.jsonl \
  --out var/bench/results/onnx-fp32-long.json
```

| 項目 | ONNX fp32 | torch（参考、CPU fp32） |
|---|---:|---:|
| 所要時間（プロセス起動とモデル読み込みを含む） | 23.30秒（RTFx 87.0） | 109.26秒（RTFx 18.5） |
| 最大RSS | 3.52GB | 6.39GB |
| macOSのピークメモリフットプリント | 3.17GB | - |
| 分割数 | 68 | 68 |
| トークン開始時刻が単調非減少か | はい | はい |
| 最後のトークンの終了時刻（音声長2,026.48秒） | 2,025.15秒 | 2,025.15秒 |
| CER strict / flex / kana（%） | 6.39 / 5.70 / 4.62 | 6.39 / 5.70 / 4.62 |

- 書き起こしの文字列はtorchとまったく同じだった。トークンの記録数（ONNX 6,174、torch 6,262）が違うのは、torchの実行後に`--timestamps`の処理が変わり、バイトフォールバックのトークンを1文字にまとめるようになったためである（`aux/long-onnx-vs-torch.txt`）。
- 1発話ずつ認識して連結した場合のCER strictは4.10%。分割による悪化はMLX版・torchと同じで、ONNXの数値誤差によるものではない。
- 出典: `var/bench/results/onnx-fp32-long.json`、`aux/long-onnx-fp32-time.txt`、torchは`torch-fp32-long.json`と`aux/long-torch-time.txt`。
